[191] (Heading 1) 4. C4 Model
[192] (Heading 2) 4.1. Container Diagram
[194] (Normal) Figure 3. Container Diagram
[195] (Normal) Prose:
[196] (Normal) The container diagram above illustrates the high-level architecture of the DBCAS system, designed to give learners and administrators a concept-level view of database competency. The system has two human roles: the Learner, who selects concepts, bands, count and source, takes learner-defined practice sessions and reads published competency results, and the Administrator, who curates course outcomes, questions, translations and rubrics, manages accounts and roles, and reviews and approves every result. Administrator-only accounts cannot take practice sessions. Both interact with the platform through a Single Page Application (SPA) built with React and Vite, delivered by the Web Application container, while core functionality is handled by the API Application built with FastAPI (Python 3.13) and reached through JSON/HTTPS APIs. The API also integrates Google and GitHub OAuth providers, sends password-reset mail through the external SMTP service (Mailpit in development), and runs an in-process background maintenance worker for session expiry and durable grading jobs; Table 50 lists these containers alongside the baseline diagram.
[197] (Normal) All persistent data is stored in a PostgreSQL 17 database (41 tables) that the API accesses via SQL, including immutable session and question snapshots, legacy assessment records, password-reset tokens and audit, result-release audit and cached LLM responses. Learner SQL is never run against this database: it is executed in a separate, isolated SQL Execution Sandbox (a Docker container running PostgreSQL 17) under a read-only role, SELECT-only validation, a 3-second statement timeout, and a 256 MB memory limit. The API Application also calls an external LLM Provider API for assistive tasks such as essay scoring against rubrics, mapping and tag suggestions, and gap explanations; final competency scores are always computed deterministically by DBCAS. OAuth sign-in is brokered through Google or GitHub; provider access tokens are never stored.

[201] (Heading 2) 4.2. Component Diagram
[203] (Normal) Figure 4 (1/2). Component Diagram — controllers, services and repositories: Auth, Practice, Curriculum and Question Bank.
[205] (Normal) Figure 4 (2/2). Component Diagram — Analytics/Competency & Gap, Grading and Accounts/Admin & Settings. The Database cylinder is repeated for connector context; it is identical to Figure 4 (1/2).
[207] (Normal) Prose:
[208] (Normal) The Component Diagram of the DBCAS system illustrates the structure of the backend implemented with FastAPI in Python. It follows a three-layer architecture of Controller, Service, and Repository layers, giving a clean separation of concerns and easier maintenance. The Controller layer receives requests from the web interface and validates them with Pydantic schemas, covering authentication and OAuth, role management, curriculum (CLOs, concepts and prerequisites), the question bank and translations, personalized assessment starts, answer attempts, grading review and analytics. Each controller delegates to a dedicated Service that encapsulates the business rules.
[209] (Normal) The Service layer is the core of the system logic: it includes the Identity & Access Service (password and OAuth sign-in, self-service password recovery, login throttling, role management), the Practice Service (session scope, complete plan freeze and idempotent starts), the Question Serving component (planned question delivery and selection logging), the Grading Service (MCQ by answer key, SQL by sandbox execution, essays by rubric), the Assessment Lifecycle & Release Service (grading jobs, human review and publication), and the Competency & Guidance Service (deterministic per-session and cumulative competency, gaps and study ranking). Two infrastructure components support these services: the LLM Gateway, which removes personal details, builds versioned prompts, enforces a strict JSON schema, and caches responses, and the Sandbox Runner, which executes learner SELECT queries in the isolated Docker sandbox. A background maintenance worker sweeps expired sessions and processes queued grading jobs with database leases. The Repository layer abstracts PostgreSQL 17 access through SQLAlchemy and performs all CRUD operations for the 41 tables. This modular design lets the team replace the LLM provider or add new question types without changing the scoring rules.

[213] (Heading 1) 5. Module View
[215] (Normal) Figure 5. Module View
[217] (Normal) Prose:
[218] (Normal) The module view of DBCAS is organized into functional modules that collaborate to deliver the assessment workflow. The Web UI Module provides the Learner and Administrator portals as a single-page application, and the API Gateway Module routes and secures every request. The Identity & Access Module handles registration, email/password and OAuth login, self-service password recovery, login throttling, role-based access control, and audited role management. The Curriculum Module manages CLOs, concepts, prerequisites and confirmed mappings, while the Question Bank Module manages validated questions, provenance, translations, version families, tags, and AI question candidates awaiting administrator approval. The Practice Module lets learners choose concepts, bands, count and source, assembles and freezes the complete question plan, runs the 30-minute session and serves the planned questions; the Grading Module scores MCQ, SQL, and essay answers, stores standardized evidence and retries failed jobs; the Result Release & Human Review Module withholds unpublished scores and provisional profiles from learners, enforces mandatory administrator review before publication and records immutable audit events; and the Competency Module computes per-session and cumulative published-evidence competency, detects gaps, ranks below-benchmark concepts for study guidance, and serves learner and cohort analytics. The AI Integration Module (LLM Gateway) and the Sandbox Module (Sandbox Runner and isolated PostgreSQL) encapsulate the two external execution paths. The Localization & Preferences Module provides English/Vietnamese content, translations, theme settings and the frozen session locale. Controllers route requests to services; repositories persist application records in PostgreSQL. Services call the LLM Gateway and SQL Sandbox only for workflows that require them.

[221] (Heading 1) 6. Allocation View
[223] (Normal) Figure 6. Allocation View
[224] (Normal) Prose:
[225] (Normal) The Allocation View for DBCAS shows how the software components are mapped onto the deployment environment. The architecture follows a multi-tier, containerized deployment pattern. The Learner or Administrator uses a laptop or desktop browser, and all traffic flows through the Internet over HTTPS to the Web Server, which serves static content and the React + Vite single-page application. Dynamic requests, such as API calls, are forwarded as JSON/HTTPS to the Application Server (FastAPI, Python 3.13), which holds the core business logic: JWT and OAuth authentication, role checks, practice session coordination, grading, personalized plan assembly, release review, and competency calculation. The same Application Server runs a background maintenance worker that expires sessions and processes durable grading jobs.
[226] (Normal) For persistence, the Application Server sends DB requests to the Database (PostgreSQL 17), which stores users, roles and audit records, the question bank, translations, sessions, attempts, immutable snapshots, evidence, release events and cached LLM responses. Learner SQL is sent to a separate SQL Sandbox container (PostgreSQL 17) that runs with a read-only role, SELECT-only validation, no network access, a 256 MB memory limit, and a 3-second statement timeout, so it can never reach application data. Finally, the Application Server calls the external LLM Provider API with sanitized, structured requests for essay scoring, mapping, tagging, and gap explanations, redirects browsers to Google or GitHub for OAuth sign-in, and sends password-reset mail through the external SMTP service (Mailpit in development; a real SMTP relay in release). Separating the sandbox and the AI service from the main application logic protects the system, keeps scoring deterministic, and improves scalability and maintainability.

[244] (Normal) Prose:
[245] (Normal) The Entity Relationship Diagram (ERD) illustrates the structure of the DBCAS PostgreSQL 17 database (41 tables) and the relationships among its entities. Account is the access point for authentication, linked one-to-one to UserProfile, optionally to AccountIdentity for OAuth, and through the AccountRole junction to Role; role changes are recorded in AccountRoleAudit and grade edits in GradeEditAudit. Administrators define CourseLearningOutcome and Concept records (with prerequisites in ConceptDependency), map them through CLOConcept, and curate the Question bank together with QuestionConcept, MCQOption, QuestionTranslation, SQLTestDataset, and Rubric. QuestionCandidate holds AI-generated drafts outside the bank until an administrator approves them. A learner-defined AssessmentSession stores its frozen plan in SessionQuestionPlan with start-request bindings, records one Attempt per served question, one SelectionLog entry per served question (is_fallback marks substitutions), and EvaluationRecord evidence for each answer; results flow through GradingJob, GradeReview and ResultReleaseEvent, and competency through ConceptCompetency and CompetencyGap. SystemSetting stores historical/operational platform values; result release is no longer selectable. The legacy Assessment, AssessmentConcept, AssessmentQuestion and AssessmentBlueprint tables are retained only for historical rows; AssessmentSession.assessment_id is nullable since migration 018. PasswordResetToken and PasswordResetAudit support single-use password recovery, RefreshSession stores hashed refresh tokens, and LLMCache, OAuthHandoff and LoginThrottle are stand-alone technical tables.

The many-to-many relationships (assigned, maps to, tagged with, targets) are realized by the junction tables AccountRole, CLOConcept, QuestionConcept and the legacy AssessmentConcept; all 41 tables are described in Table 54.
