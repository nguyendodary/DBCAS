T6R0: No. | Learning Area / Topic | Common Difficulties Discussed Online | How DBCAS Solves It
T6R1: 1 | Single Overall Grades | Learners on learning forums often state that getting a single test score (such as 7 or 8 out of 10) tells them they passed, but gives them no idea which specific database concepts they actually mastered and which ones need review. | Calculates competency scores across core PostgreSQL concepts and displays an interactive visual radar chart of strengths and weaknesses.
T6R2: 2 | Database Normalization Rules | A common complaint on developer communities is that normalization rules (1NF, 2NF, 3NF, BCNF) feel too theoretical, and learners struggle to explain why a bad schema design leads to data duplication or update anomalies. | Provides short written conceptual questions evaluated using clear rubrics that explain why an answer is incomplete and how to fix the design.
T6R3: 3 | Complex SQL Queries (JOINs & Aggregates) | Learners frequently ask questions about multi-table joins, GROUP BY, and subqueries, finding it frustrating when existing practice sites only say 'Wrong Output' without helpful hints. | Runs queries in an isolated Docker container and checks both the query structure and returned rows to give helpful hints on mistakes.
T6R4: 4 | Lack of Diagnostic Explanations | Discussions show that standard multiple-choice quizzes only show correct or incorrect marks without explaining the underlying concept behind a wrong answer. | Identifies the core concept behind missed questions and provides clear written explanations to help learners understand why an answer was wrong.
T6R5: 5 | One-Size-Fits-All Exams | A common frustration is that fixed exams give every learner the same question set, so strong learners waste effort on easy items while weaker learners face items far above their level, and neither group gets an accurate ability reading. | Freezes the learner's chosen concepts, difficulty bands, count and source before question one, then assembles and freezes a complete practice plan that is spread across the selected concepts as far as the count allows without repeating question families; SQL always comes from the validated bank.

T13R0: Category | Constraint / Assumption Item | Detailed Technical Scope & Rationale
T13R1: Technical Constraints | SQL Sandbox Resource Limits | Learner SQL queries run inside a dedicated Docker sandbox container with memory capped at 256 MB and execution capped at 3 seconds via statement_timeout to prevent server overloads or runaway queries. The sandbox accepts read-only SELECT statements only; DML/DDL are assessed through MCQ and essay.
T13R2: Technical Constraints | External LLM Provider Limits & Latency | External language model API calls are managed using PostgreSQL-backed response caching, durable asynchronous grading jobs in the FastAPI backend, and a cost-effective model from the configured provider to avoid delays.
T13R3: Technical Constraints | Modern Web Browser Compatibility | The web interface runs smoothly on standard modern browsers (Chrome, Edge, Firefox, Safari) using standard HTML5/CSS without requiring custom browser plugins.
T13R4: Technical Constraints | OAuth Provider Integration | Google/GitHub sign-in and sign-up use signed state, Google PKCE, verified email and a single-use handoff. Login and Register always show both choices; an unconfigured provider offers email sign-in. Matching verified emails link one account without changing roles. Both email and OAuth issue rotating access/refresh sessions; provider tokens are never stored or exposed to the browser.
T13R5: Academic & AI Ethics | Administrator-Configured Evaluation & Assistive AI | The external LLM Provider assists with essay scoring against administrator-configured rubrics and generates evidence-linked gap explanations; it does not determine final competency. Administrators configure essay rubrics and review every submission; the platform applies a 70% passing target per concept. DBCAS deterministically aggregates recorded answer evidence into concept scores and ranks below-benchmark concepts by shortfall; every submission requires administrator approval of SQL and essay scores before publication. Gap explanations cannot change scores or order.
T13R6: Academic Constraints | 15-Week Capstone Timeline | All design, implementation, testing, and documentation must conclude within the university 15-week Capstone 1 timeframe, finishing with formal defense in late December 2026.
T13R7: Academic Constraints | Independent Benchmark Test Data | To avoid administrative delays obtaining live university student records, the team utilizes a self-contained benchmark dataset of sample questions, schemas, and answers.
T13R8: Project Assumptions | Learner Background Knowledge | Learners using the platform possess basic computer literacy and have attended introductory lectures on relational database concepts and basic SQL syntax.

T18R0: No. | Prompt Design Principle | Technical Implementation in DBCAS | Quality & Fairness Safeguard
T18R1: 1 | Deterministic Scoring Controls | API temperature is set to a low value (temperature = 0.1) with fixed seeds across repeated calls. | Prevents random score variations and ensures identical learner answers receive consistent grades.
T18R2: 2 | Strict JSON Output Schema | Language model output is constrained to a predefined JSON schema containing numeric scores, rubric levels, and cited text. | Enables reliable automated parsing by the FastAPI backend and prevents free-form text hallucinations.
T18R3: 3 | Rubric-Guided Few-Shot Prompts | Prompts include explicit rubric level definitions (Complete, Mostly Complete, Partial, Incomplete) with concrete grading examples. | Ensures the AI acts strictly as an objective rubric evaluator rather than an unconstrained chatbot.
T18R4: 4 | Administrator-Configured Evaluation Rules | Administrators configure essay rubrics and review every submission, apply the platform's 70% passing target, and approve AI-generated question candidates before bank entry. The LLM provides rubric-assisted essay scores and evidence-linked gap explanations. DBCAS applies fixed rules to recorded answer evidence to compute concept competency and rank gaps by shortfall; gap explanations do not change scores or order. Every submission requires administrator approval of SQL and essay scores before publication. | Keeps evaluation rules and validated question content under Administrator control, with defined system rules for scores and rankings and human sign-off where required.

T19R1: RSK-01Technical / Security | Learners writing harmful SQL queries or infinite loops that could overload the server. | Likelihood: LowImpact: High | • Enforce a strict 3-second statement timeout and a 256 MB memory limit on the sandbox container. • Run queries in an isolated, unprivileged container under a read-only role and accept SELECT statements only; DML/DDL are assessed through MCQ and essay. • Roll back every learner transaction and reset the sandbox schema between assessment sessions.
T19R2: RSK-02AI Consistency | Language model giving slightly different scores or inaccurate feedback on written essay answers. | Likelihood: MediumImpact: Medium | • Use low temperature settings and require structured JSON output. • Grade using detailed rubrics that require citing specific sentences from learner answers. • Route every session through the administrator review queue and publish only after approval.
T19R3: RSK-03API Cost & Latency | External LLM Provider fees or slow network responses during busy assessment sessions. | Likelihood: MediumImpact: Medium | • Use a fast, cost-effective model from the chosen LLM provider. • Cache identical evaluation queries in a PostgreSQL table and process grading as durable asynchronous jobs.
T19R4: RSK-04Dataset Access | Limited access to real university learner exam archives due to school privacy policies. | Likelihood: HighImpact: Medium | • Build a self-contained benchmark dataset of realistic, difficulty-tagged sample questions, schemas, and answers large enough to support personalized plan assembly. • Include common learner mistakes to test the evaluation pipeline thoroughly.
T19R5: RSK-05Schedule Delays | Sprint tasks running behind schedule, risking university review deadlines. | Likelihood: MediumImpact: High | • Follow strict two-week sprints with velocity tracking at every retrospective.• Focus on completing core features first for a solid Midterm demonstration.
T19R6: RSK-06 Personalized Plan Quality | A personalized selection repeatedly over-samples narrow or poorly matched questions, producing an inaccurate ability estimate. | Likelihood: LowImpact: Medium | • Spread the plan across the selected concepts as far as the count allows: freeze the complete practice plan before serving and disclose any widening to related concepts or bands. • Log every selection decision and use validated fallback items so no session waits for AI generation.
