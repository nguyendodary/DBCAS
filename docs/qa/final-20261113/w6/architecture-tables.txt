T15R0: ID | UC02
T15R1: Title | Login
T15R2: Description | Allows learners and administrators to authenticate securely with email/password or Google/GitHub, recover a forgotten password by email, and access role-specific functionality.
T15R3: Entities Involved | E01: Administrator, E02: Learner, E03: Learner before sign-in, E05: OAuth Identity Provider
T15R4: Preconditions | The user has an active account or a provider-verified email for account linking or Learner sign-up. Email/password login is subject to throttling.
T15R5: Primary Flow | 1. Login and Register show Google/GitHub choices; an unconfigured provider offers email sign-in. 2. For email/password, the system verifies the credentials and active status; repeated failures are throttled server-side. If the password is forgotten, the login page offers a recovery flow: the API returns the same acknowledgement for every address, emails a single-use 15-minute token only for an active account when mail delivery is configured, and stores only its SHA-256 digest. The reset form applies the same password policy and invalidates earlier login sessions. 3. For Google/GitHub, the backend redirects with a signed state cookie (and PKCE for Google), validates the state-bound callback and configured redirect URI, and exchanges the code server-side. 4. The account is resolved by an existing identity link, then a verified email, otherwise a new active Learner is created; verified-email linking preserves existing roles. 5. The SPA consumes the handoff once for rotating access/refresh tokens, as with email sign-in; provider tokens are never stored or exposed in URLs. 6. System loads current database roles and redirects to the learner or administrator dashboard.
T15R6: Postconditions | The user reaches the dashboard for their role. New OAuth accounts start as Learners; existing roles are preserved and disabled accounts are refused.
T15R7: Alternate Flows | A1: Invalid credentials -- Display an error message and apply throttling. A2: Account disabled (for example, a newly provisioned administrator not yet activated) -- Login is refused. A3: OAuth state or PKCE mismatch, expired handoff, or unverified provider email -- The flow is rejected and no account is linked. A4: Unauthenticated visit to a protected page -- Redirect to the login page. / A5: Password-reset token is expired, used, revoked or unknown -- The reset is refused with a generic invalid-link message. / A6: Reset mail delivery is not configured -- The request fails closed with password_reset_unavailable while the response still does not reveal whether the address exists.

T17R2: Description | Allows authorized role managers to provision accounts and grant or revoke Learner/Administrator roles under controlled activation and immutable audit. A Learner may request promotion to Administrator; an authorized role manager handles the request through this use case, and DBCAS exposes no self-service promotion endpoint.
T17R3: Entities Involved | E01: Administrator
T17R4: Preconditions | Signed in as an Administrator with Account.status = active and can_manage_roles = true.

Grant or revoke role submits the expected current role; the server serializes the change and re-checks the capability. 5. Every change is written to AccountRoleAudit; the one-time role-manager bootstrap is recorded separately.

A3: Change would remove the last administrator or role manager -- Rejected. A4: Self-registration can never grant the Administrator role. A5: Learner requests promotion -- An authorized role manager verifies that the account is active, grants the Administrator role through this audited flow, and role-management capability is not granted automatically.

T25R0: ID | UC12
T25R1: Title | Take a Personalized Practice Session
T25R2: Description | Allows learners to choose concepts, difficulty bands, an exact question count and a source, then complete a practice session whose complete plan is frozen before question one.
T25R3: Entities Involved | E02: Learner
T25R4: Preconditions | The learner is logged in and validated questions exist for the selected concepts and bands.
T25R5: Primary Flow | 1. Learner selects one or more concepts and one or more difficulty bands: EASY 1–2, MEDIUM 3, or HARD 4–5. 2. Learner chooses an exact question count from 1 to 20 (default 5) and a source: the validated bank or AI. 3. Learner starts the session; the server verifies the requested count against the approved bank, assembles the complete ordered plan, freezes it and creates the session with expires_at = started_at + 30 minutes. 4. In AI mode the planner requests MCQ and essay items from the model, always takes SQL items from the validated bank, and validates every generated item before it enters the plan; if AI cannot fill the plan, a single bank_mixed notice explains the substitution. 5. The interface shows a persistent countdown with warnings at 10 and 5 minutes and a progress indicator; navigation is forward-only. 6. The session ends after the planned questions or at 00:00; answers enter the grading and release pipeline.
T25R6: Postconditions | The session, its frozen plan and standardized evidence are stored; the result appears only after administrator review and approval.
T25R7: Alternate Flows | A1: Duplicate start request -- The existing session is returned. A2: The approved bank cannot supply the requested count for the selected concepts and bands -- The start is rejected with a clear insufficient-pool error. A3: Timer reaches 00:00 -- Answers are submitted automatically and the session status becomes timed_out. A4: Grading fails -- The attempt enters the durable retry queue and the session reports grading_failed until resolved. / A5: AI mode cannot fill the plan -- The plan is completed with validated bank items and a single bank_mixed notice is shown. / A6: A generated question fails validation -- It is discarded before the plan is frozen; an invalid plan is never served.
T26R0: ID | UC13
T26R1: Title | Write and Run SQL in the Embedded Editor
T26R2: Description | Allows learners to solve SELECT query tasks in a safe environment.
T26R3: Entities Involved | E02: Learner
T26R4: Preconditions | A session is in progress and the current question is a SQL task.
T26R5: Primary Flow | 1. Learner views the schema viewer for the test tables. 2. Learner writes a query in the editor with syntax highlighting and runs or submits it. 3. The API validates that the statement is a single SELECT; DML/DDL and other statements are rejected before execution. 4. The query runs in the isolated PostgreSQL 17 Docker sandbox under a read-only role, a 3-second statement timeout, and a 256 MB memory limit, inside a read-only transaction that is rolled back. 5. The result or a clear error message is shown to the learner.
T26R6: Postconditions | The query result is recorded as the learner's SQL answer for grading.
T26R7: Alternate Flows | A1: DML/DDL or a non-SELECT statement -- Rejected with a message that these topics are assessed only through MCQ/essay. A2: Statement timeout -- Display a clear timeout message. A3: SQL error -- Display the error and a helpful hint.

T28R0: ID | UC15
T28R1: Title | Receive Grading Results and Feedback
T28R2: Description | Scores every answer on submission and queues every submitted session for administrator review and approval.
T28R3: Entities Involved | E02: Learner, E04: LLM Provider
T28R4: Preconditions | The learner has submitted an answer.
T28R5: Primary Flow | 1. MCQ answers are compared instantly with the verified answer key. 2. SQL answers are executed in the sandbox against multiple test datasets, including edge cases, and graded by semantic and result correctness (and required-concept usage when a technique is mandated), never by exact string matching. 3. For essays, the system removes learner names and identifying numbers, then calls the LLM Provider with the four-level rubric, a low temperature, and a strict JSON schema. 4.
