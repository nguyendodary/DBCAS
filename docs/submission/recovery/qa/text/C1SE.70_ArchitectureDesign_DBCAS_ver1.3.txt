[Heading 1] 1. Introduction
[Heading 2] 1.1 Purpose and Scope
This document specifies the architecture of DBCAS, an AI-assisted database competency assessment system. It covers the architectural drivers, the system context, the container and module views, the main runtime flows, the AI pipeline, the SQL sandbox, grading and result versioning, security, the architectural decisions and the key algorithms. Requirements and schedule are in the Proposal; the schema and its dictionary are in the Database Design document; coding rules are in the Code Standards document.
[Heading 2] 1.2 How this Document Was Measured
Every structural statement is derived from the repository at the frozen commit: 106 OpenAPI paths and 118 operations generated from the running FastAPI application, 8 router modules, 73 service modules, 13 repository classes in one module, 25 React route elements with 24 distinct paths, and six Compose services in the default local profile. Figures are generated from docs/diagrams sources, not drawn for this document.
[DBCAS Note] Owner-facing caveats are marked [OWNER TO PROVIDE: ...]. They are collected in section 14 and in the verification report.
[Heading 1] 2. Architectural Drivers
[Heading 2] 2.1 Functional Drivers
[List Bullet] Two human actors only: Learner and Administrator. Everything a learner sees is derived from their own attempts; everything an administrator does is auditable.
[List Bullet] Three answer formats with different execution semantics: stored options for MCQ, executed SQL for SQL, rubric text for essays.
[List Bullet] A practice plan that is frozen before the first question, so the session is reproducible and cannot be silently shortened.
[List Bullet] Publication gated by evidence: practice and legacy sessions need administrator review, fixed-test sessions publish an official V1.
[List Bullet] AI used only where it adds value (rubric assistance, question generation), always behind validation and a deterministic fallback.
[Heading 2] 2.2 Quality Attributes
[DBCAS Caption] Table 1. Quality attribute scenarios and their architectural response
[Heading 2] 2.3 Constraints
The system is a single-host Docker Compose deployment. PostgreSQL 17 is the only durable store. The sandbox is a throw-away PostgreSQL container started through the Docker API, so the host Docker socket is a deployment dependency. The AI provider is an external OpenAI-compatible endpoint configured only by key, base URL and model name; no model weights are stored. These constraints are repeated as C1–C10 in the Proposal and are not re-derived here.
[Heading 1] 3. System Context
The context view has two human actors and three external systems. The learner sends practice requests, answers and view requests; the administrator sends curriculum, bank, rubric and review requests. The system calls the LLM provider for essay evaluation and question generation, redirects to Google or GitHub for OAuth, and sends password-reset mail through SMTP.

[Heading 1] 4. Overall Architecture
[Heading 2] 4.1 Logical Tiers
DBCAS is a four-tier application: presentation (React 19 and Vite), application programming interface (FastAPI on Python 3.13), data (PostgreSQL 17 through SQLAlchemy) and execution (an ephemeral PostgreSQL container used only to run learner SQL). The browser never reaches the database; the API is the only client of the database and of the execution tier.
[DBCAS Caption] Figure 2. Logical architecture: presentation, API, data and execution tiers
[Heading 2] 4.2 Containers
[DBCAS Caption] Table 3. Containers in the default local profile
A seventh service, qa-ai, exists only in the QA Compose profile and returns deterministic fake provider JSON so browser tests never call a real model. The execution container is not a Compose service: it is created per SQL execution with a random name, labelled with its owner, and removed on exit.
[Heading 2] 4.3 Backend Layering
The backend is layered by responsibility. Routers declare HTTP contracts and dependencies; services hold use cases and transactions; repository classes hold queries. The repository layer has 13 repository classes in a single module of about 1 700 lines; models and schemas are single modules as well. The dependency direction is one-way: repositories import no service and services import no router. Six router handlers still query the session directly, which the Code Standards document records as a known exception rather than a rule.
[DBCAS Caption] Figure 3. Module view: routers, services, repositories and shared infrastructure
[Heading 2] 4.4 Frontend Structure
The frontend is a single-page application with 25 route elements over 24 distinct paths, role-guarded at the route level. Server state is fetched through one API client with a /api/v1 base URL; the client maps machine-readable error codes to localised messages, so a backend error code is also an i18n key. Interface text and question translations are separate catalogues: 1 700 leaf keys in English and the same 1 700 in Vietnamese, with zero drift.
[Heading 1] 5. Main Flows
[Heading 2] 5.1 Sign-In and Session Establishment
1. The browser posts credentials to /api/v1/auth/login, or follows the OAuth redirect for Google or GitHub.
2. The API verifies the password hash, applies the login throttle, and issues a short-lived access token plus a refresh token.
3. Every later request carries the access token; the dependency layer resolves the account and its capabilities.
4. A refresh rotates the refresh token; a reused token is rejected.
[Heading 2] 5.2 Practice Session Start
1. The learner chooses concepts, difficulty bands, question count within the published limits, and source (bank or AI).
2. The API opens a transaction, takes an advisory lock for the learner-assessment pair, and looks for a live session to make start idempotent.
3. The planner builds the complete plan: exact count, per-format quotas, concept spread and no repeated version family.
4. With the AI source, MCQ and essay items may be generated and validated first; SQL items always come from the validated bank.
5. The plan and its configuration snapshot are persisted and the first question is served. A bank shortage aborts the start with an explicit error instead of a shorter session.
[Heading 2] 5.3 Answer Submission and Grading
1. The answer is submitted with the question identifier; the attempt row is locked and ownership is re-checked.
2. A repeated submission with the same answer hash returns the stored result; a different answer is rejected with 409.
3. MCQ is scored by exact option matching; SQL is executed in the sandbox and compared with the expected grid or table state; essay text is graded by the rubric pipeline.
4. When the provider or the sandbox fails, the answer is kept and a durable grading job is queued; nothing is fabricated.
5. A background worker claims the job with a lease, grades it, and publishes either the grade or an explicit failure.
[Heading 2] 5.4 Result Publication and Review
1. For a fixed-test session the finalize transaction publishes an official V1 result version with per-question and per-criterion scores.
2. For practice and legacy sessions the result stays pending until an administrator reviews it.
3. A learner may request a review inside a seven-day window with a reason; the request is idempotent by header key.
4. An administrator claims the case with a 30-minute lease, then rejects it or regrades it; a deviation above 30 % needs explicit confirmation.
5. The learner's cumulative profile is recomputed from published sessions only, so an unpublished session cannot move the profile.
[Heading 2] 5.5 Competency Recompute
Concept scores are recomputed from published evidence, not incremented in place: identical evidence rewrites identical values. The computation is therefore safe to repeat after a regrade, a review decision or a worker restart, and a gap record is created only when the recomputed score is below the 70 % target.
[Heading 1] 6. AI Pipeline
Two AI roles are separated. The first builds the evaluation prompt with a deterministic template and is not a model call; it always reports builder_fallback true because no model is used for prompt construction. The second calls the provider and is the only place where a model is involved.
[DBCAS Caption] Figure 4. AI pipeline: prompt assembly, provider call, validation, fallback and publication
[Heading 2] 6.1 Question Generation
1. An administrator selects a concept, a difficulty band and a type, and supplies a generation request identifier.
2. The request digest is computed over the payload and the administrator; a replay returns the stored candidates and a changed payload is rejected.
3. The provider returns structured JSON; the candidate is stored as a draft, never as a servable question.
4. An administrator reviews and approves the candidate before it can enter the validated bank.

[Heading 2] 6.4 Review Queue
Review cases move through REQUESTED, IN_REVIEW, REGRADED, REJECTED and EXPIRED. A claim is a lease of 30 minutes; an expired claim returns the case to the queue rather than deciding it. The worker never approves or rejects on the learner's behalf. A regrade that moves a score by more than 30 % requires a confirmed deviation before it can be published.

[Heading 1] 7. SQL Sandbox
[Heading 2] 7.1 Two Modes
By default every statement runs read-only. The opt-in writable demo profile allows DML and DDL inside the ephemeral container, captures the resulting table state, and then destroys the container, so the write never reaches the application database.
[Heading 2] 7.2 Isolation Controls
[DBCAS Caption] Table 7. Sandbox container controls
[Heading 2] 7.3 Statement Policy
The policy is AST-based: the script is parsed, statement types and functions are checked against an allowlist, and unknown constructs fail closed. A read-only database role is granted separately, so a parser gap still cannot write. Multi-statement scripts are off by default and, when enabled, are bounded by statement count, total time and rows.
[Heading 2] 7.4 DML Table-State Grading
A data-manipulation task is graded on the state it leaves behind, not on the rows a SELECT would return. The expected result declares the tables to capture, whether order matters, and whether a table must be missing. After execution the captured state is compared table by table: missing tables fail first, then column sets, then rows as an ordered list or as a multiset. The first failing table names the reason, so feedback can say which table diverged.
[Heading 1] 8. Grading and Result Versions
[Heading 2] 8.1 Scoring
[List Bullet] MCQ: the selected option is compared with the keyed option; the score is the question weight.
[List Bullet] SQL: the result grid is normalised (value kinds, row order, column order) and compared with the expected grid, or the captured table state is compared with the expected state.
[List Bullet] Essay: rubric criteria are scored within their maxima; the provider may assist, and the deterministic rubric is used when it cannot.
[List Bullet] Every score is stored with the question version and the rubric profile version that produced it.
[Heading 2] 8.2 Status Vocabularies
[DBCAS Caption] Table 8. Grading and publication statuses
[Heading 2] 8.3 Result Versions
A session points at exactly one current result version. The official V1 is created once, inside the finalize transaction; a late caller reuses it instead of creating a second version. A regrade creates a new version and moves the current pointer, so the previous result remains readable and the learner sees which version is current.

[Heading 1] 11. Key Algorithms
[Heading 2] 11.1 Adaptive Difficulty
Selection is deterministic: every tie-break ends in the question identifier, so the same state always yields the same question.
[DBCAS Code] pick(assessment, attempts, pool):
[DBCAS Code] served = len(attempts)
[DBCAS Code] if served < 3:                      # opening: three basic MCQs
[DBCAS Code] choose the easiest MCQ covering a concept not yet seen
[DBCAS Code] if served == 3:                     # opening verdict sets the Q4 level
[DBCAS Code] correct = count(score >= points)
[DBCAS Code] bias = 3 if correct == 3 else 2 if correct == 2 else 1
[DBCAS Code] wanted = type with the highest quota pressure (need / slots left)
[DBCAS Code] concept = an uncovered target, else the weakest concept
[DBCAS Code] if bias:        preferred = clamp(bias, min_d, max_d)
[DBCAS Code] elif last_correct: preferred = min(last_d + 1, max_d)
[DBCAS Code] else:           preferred = max(last_d - 1, min_d)
[DBCAS Code] return argmin over candidates of
[DBCAS Code] (abs(difficulty - preferred), difficulty, question_id)
Only validated questions with a confirmed tag to a target concept inside the configured difficulty range are eligible, so an AI draft can never be served directly. Each serve writes one selection log row and marks is_fallback when the served type differs from the wanted type or a constraint had to be relaxed.
[Heading 2] 11.2 DML Table-State Grading
[DBCAS Code] compare_state(actual, expected):
[DBCAS Code] if {a.table} != {e.table}: fail("tables")
[DBCAS Code] for each expected table:
[DBCAS Code] if expected.missing:            pass iff actual.missing
[DBCAS Code] elif actual.missing:            fail("<t>:missing")
[DBCAS Code] elif expected.columns and actual.columns != expected.columns:
[DBCAS Code] fail("<t>:columns")
[DBCAS Code] elif expected.ordered:          compare row tuples with ==
[DBCAS Code] else:                           compare row multisets
[DBCAS Code] return passed iff no failure
[Heading 2] 11.3 Idempotency
Four independent keys make retries safe: the answer submission hash returns the stored result for the same answer and rejects a changed one; the session start request identifier returns the existing live session; the review Idempotency-Key header returns the existing case; and the generation request digest returns the stored candidates. Cross-owner reuse of a key is a conflict, not a replay.
[Heading 2] 11.4 Job Lease
[DBCAS Code] claim_grading_job(include_essay, lease_seconds=180):
[DBCAS Code] select job  where status = 'pending' and available_at <= now()
[DBCAS Code] or status = 'processing' and lease_until < now()
[DBCAS Code] order by available_at  limit 1  for update skip locked
[DBCAS Code] set status = 'processing', lease_until = now() + lease
[DBCAS Code] commit                                  # provider work holds no lock
After grading, the worker re-reads the job and publishes only if the attempt count and the lease are unchanged; otherwise another worker has recovered the lease and the result is dropped. A failure requeues with a backoff of retry seconds multiplied by the attempt number, and the third failure marks the job failed. The same compare-and-set pattern protects the two-stage AI audit.
