[Heading 1] 1. Purpose and Scope
This document records the coding standards that the DBCAS repository actually applies, and separates them from advice. A rule appears here only if a configuration file, a script, a hook or a CI job enforces it, or if the repository states it as review policy. Where the project does not enforce something that a standard document usually claims, this document says so.

[Heading 1] 4. Backend Layering
The backend separates HTTP contracts, use cases and queries. Routers declare paths, request models and dependencies; services own transactions and rules; repository classes own SQLAlchemy queries and locks. The dependency direction is one-way and is checked in review: no repository imports a service, no service imports a router.
[DBCAS Caption] Table 3. Layer responsibilities
One measured exception exists: six router handlers query the session directly (practice.py lines 148 and 167, sessions.py 167, admin.py 227 and two adjacent handlers). They are listed here as known debt, not as an accepted pattern, and a change touching them should move the query into a repository method.
[Heading 1] 5. API Conventions
[List Bullet] Versioning is a URL path segment: every business route is under /api/v1. Two infrastructure routes (/health and /readiness) are unversioned by design.
[List Bullet] Resources are plural nouns; actions that are not CRUD use a verb segment (/sessions/{id}/submit, /admin/reviews/{id}/claim).
[List Bullet] Request and response bodies are Pydantic models; a handler never returns a raw ORM object.
[List Bullet] The OpenAPI document is generated from the application and checked into CI: python scripts/export_openapi.py --check fails when the committed contract differs from the code.
[List Bullet] Machine-readable errors use the envelope {error: {code, message, details}} with a stable lower_snake_case code; the frontend translates by that code, so a code is part of the public contract.
[List Bullet] List endpoints paginate with limit and offset and return the total when the UI needs it; a missing bound is a review finding.
[List Bullet] Authentication is a bearer token resolved by a dependency; authorisation is a capability check in the same dependency chain, never an if-statement in a handler.
[DBCAS Caption] Table 4. Status code usage
[Heading 1] 6. Error Handling
One application exception class, AppError, carries a status code, a machine-readable code, a human message and optional details. Seven handlers translate exceptions at the boundary: LLM errors, database programming and operational errors, the catch-all, AppError, HTTP exceptions and request-validation errors. The catch-all re-applies the security headers because it short-circuits the middleware, a detail that must be preserved in any refactor.
[List Bullet] Raise AppError with a new code rather than returning an error body from a handler.
[List Bullet] Never leak a driver message, a stack trace or a prompt to the client.
[List Bullet] Log the code and the identifiers, never the answer text or the key.
[List Bullet] A provider failure must degrade to a documented fallback; an unexpected validation failure must not fabricate a score.
[Heading 1] 7. Frontend Conventions
[List Bullet] Components are function components with hooks; no class components.
[List Bullet] Data access goes through the single API client, which owns the base URL, the bearer token and error-code translation.
[List Bullet] Route guards check the role at the route level; a page does not re-implement authorisation.
[List Bullet] Every user-visible string is an i18n key; a literal string in JSX is a review finding.
[List Bullet] Charts read prepared series from the API; no scoring is recomputed in the browser.
[List Bullet] Styling uses Tailwind utility classes; shared visual tokens live in one place.
[Heading 1] 8. Internationalization
English and Vietnamese catalogues are flat JSON with the same key set: 1 700 leaf keys in 34 groups in each language, zero drift. Question text is translated separately in the database, with English as the canonical original and a source hash per translation. Error codes are also i18n keys, so a new backend code requires a matching entry in both catalogues.
[Heading 1] 9. Testing Standards
[DBCAS Caption] Table 5. Test layers
[List Bullet] A bug fix adds a regression test that fails before the fix.
[List Bullet] A test never calls a real provider: the QA profile serves deterministic fake JSON.
[List Bullet] A test may not be skipped or weakened to make a gate pass; a skip must name the reason in the test.
[List Bullet] There is no coverage threshold. Coverage is not measured anywhere in the repository, so no percentage is claimed in this document.
[Heading 1] 10. Lint and Format
[DBCAS Caption] Table 6. Configured tools
Python formatting is not automated: there is no ruff format configuration and no formatter job. Python style is therefore a review standard. Line endings are normalised at the Git layer (.gitattributes) so the formatter sees the same text on Windows and Linux.
[Heading 1] 11. Commit and Branch Conventions
Commits follow Conventional Commits: <type>(<scope>): <description>, with ten accepted types (feat, fix, docs, style, refactor, test, chore, perf, ci, build), a lowercase imperative description of 50–72 characters without a trailing period, and an optional body of lines up to 72 characters. One commit does one thing. The integration branch is develop2; main receives merges by pull request only.
Attribution is the one mechanically enforced part: the commit-msg hook rejects AI or tool credit trailers and bot co-authors. The message format itself is a review standard, not a hook or a CI gate; the repository has no commitlint job.
[Heading 1] 12. Pull Requests and CI
The pull request template requires a summary, a verification list (tests, lint and format, manual verification, STATUS and BACKLOG when state changed), a risk section naming affected users and data with a rollback path, migration and breaking-change flags, and an independent-review flag.
[DBCAS Caption] Table 7. CI workflows and jobs
There is no coverage job, no static-analysis security job beyond the dependency audits and the custom frontend audit, and no type-checking job.
[Heading 1] 13. Secret Handling
Secrets live in the environment only. .env is ignored and never committed; .env.example documents every variable name and is checked by the environment inventory gate. The scanner applies seven patterns to the working tree, to staged blobs in the pre-commit hook, and to archives up to 128 MiB; it reports paths, never values.
[List Bullet] The allowlist has six entries, each pinned by path, rule, SHA-256 and a reason that must start with “Fake fixture:”; it cannot be widened to hide a real secret.
[List Bullet] A finding is fixed at the source; deleting the line from history is an owner decision, not a routine fix.
[List Bullet] The measured result at this commit is zero findings in the tree and zero matching commits in history.
