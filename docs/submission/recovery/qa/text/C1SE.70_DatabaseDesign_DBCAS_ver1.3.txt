[Heading 1] 1. Introduction
[Heading 2] 1.1 Scope
This document describes the DBCAS relational schema: its conventions, its entity-relationship overview, the table registry, the column dictionary, keys and indexes, the migration history, the seed data, and the snapshot, version and audit layers. It is the reference for the persistence contract used by the API described in the Architecture Design document.
[Heading 2] 1.2 How This Document Was Measured
Every object below was read from PostgreSQL 17.12 introspection of db/schema.sql after all 28 migrations, recorded in docs/diagrams/schema-028/schema-introspection.json and gated by docs:check. The application schema has 67 tables and 561 columns, 122 foreign keys and 159 indexes. The migration ledger table schema_migration is excluded from these counts because it is runtime bookkeeping, not domain data; the live database therefore shows one table and three columns more than this document.
[DBCAS Caption] Table 1. Measured schema totals
[DBCAS Note] The four assessment-prefixed tables are retained legacy objects. They are present in the schema, marked as legacy in the ERD, and are not written by current code paths.
[Heading 1] 2. Conventions
[List Bullet] Names are lower_snake_case. A table is singular and names the entity (account, question, attempt); join tables concatenate both entities (question_concept).
[List Bullet] Every table has a surrogate primary key named <table>_id, except tables whose identity is the pair itself.
[List Bullet] Foreign keys are named <table>_<column>_fkey by PostgreSQL and are declared with an explicit ON DELETE policy; no cascade deletes domain history.
[List Bullet] Timestamps are timezone-aware and default to now(); audit tables are append-only and protected by triggers.
[List Bullet] There is no soft-delete flag and no tenant column: the deployment is single-institution, and history is preserved in dedicated tables rather than by hiding rows.
[List Bullet] Constraint names are stable and referenced by the API error codes, so renaming requires a migration and a code change together.

[Heading 1] 6. Keys and Indexes
The schema declares 122 foreign keys and 159 indexes. Of the indexes, 68 are primary-key indexes, 41 back a unique constraint and 51 are standalone performance indexes created explicitly by db/schema.sql.
[DBCAS Caption] Table 4. Key and index inventory
Index rules applied: every foreign-key column is indexed because the API filters attempts by session, questions by concept and audit rows by actor. Status columns used by the worker are indexed with the timestamp that orders them, so the job claim query never scans the table. Two known gaps remain and are listed in section 10: mcq_option.question_id and rubric.question_id have no index of their own.
[Heading 1] 7. Migrations
28 forward-only migrations are applied in order inside one transaction under an advisory lock. The runner stores the SHA-256 of each file in schema_migration and refuses to run if an applied file changed, so an edited migration must become a new file. There is no down-migration path.

Seed data has three independent sources, each idempotent by a different mechanism.
[DBCAS Caption] Table 6. Seed sources

[Heading 1] 9. Version, Snapshot and Audit
[Heading 2] 9.1 Result Versions
A published result is immutable. session_result_version stores one row per version with the source (V1 or V2), a supersedes pointer, the result hash and the approving administrator; session_result_version_score stores the per-attempt scores and session_result_criterion_score the per-criterion scores. session_result_publication is the only mutable row and carries a revision counter that guards every transition.
[Heading 2] 9.2 Snapshots
[List Bullet] assessment_session.config_snapshot freezes the session configuration chosen by the learner.
[List Bullet] attempt.question_snapshot freezes the question text served, so a later edit cannot change a historical answer.
[List Bullet] attempt_rubric_criterion freezes the rubric criterion and its maximum at grading time.
[List Bullet] question_rubric_profile and its criteria are versioned by profile_hash, so a rubric edit creates a new profile.
[List Bullet] question.family_id and version_no give each question a lineage; a session may not contain two versions of the same family.
[Heading 2] 9.3 Audit
[DBCAS Caption] Table 7. Audit tables
Immutability is enforced by database triggers, not by convention: 36 row-level guards reject updates and deletes on the audit and result tables, and five constraint triggers validate that a result version is complete and totals match before publication.
[Heading 1] 10. Maintenance Notes and Open Items
[List Bullet] schema_migration is runtime bookkeeping and must not be seeded or edited by hand.
[List Bullet] Two foreign-key columns still lack a dedicated index: mcq_option.question_id and rubric.question_id. This is a known performance gap, not a correctness defect.
[List Bullet] assessment_session.result_release_policy mixes a policy value with lifecycle states; a future migration should split the vocabulary.
[List Bullet] The duplicate concept_dependency definition recorded in the backlog remains an owner decision.
[List Bullet] updated_at is maintained by the application, not by a trigger.
