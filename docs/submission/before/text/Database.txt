[P064] [Heading 1] Introduction
[P065] [Normal] The Database Design maps the logical data model to the target database management system, considering the system’s performance requirements. It converts logical or conceptual data constructs to physical data constructs (e.g., tables, etc.) of the target Database Management System.
[P066] [Heading 2] Purpose
[P067] [Normal] The Database Design aims to ensure that every database transaction of the DBCAS platform — learner accounts, account recovery, the concept taxonomy, the question bank, learner-defined practice sessions, attempts, and competency results — is processed and stored reliably. It describes the PostgreSQL 17 schema that persists all application data for the AI-assisted database competency assessment and skill gap analysis system.
[P068] [Heading 2] Scope
[P069] [Normal] The Database Design Document has the following objectives:
[P070] [List Paragraph] To describe the design of a database, that is, a collection of related data stored in the PostgreSQL DBMS, which supports the DBCAS practice workflow (CLO mapping, question banking, SQL sandbox evaluation, rubric grading, and competency gap reporting).
[P071] [List Paragraph] To serve as a basis for implementing the database and related software, including the FastAPI backend, the Docker-isolated PostgreSQL sandbox, and the LLM-assisted grading pipeline.
[P072] [Heading 2] Introduction about PostgreSQL
[P073] [Normal] PostgreSQL is a powerful open-source relational database management system (RDBMS) known for standards compliance, reliability, and extensibility. It supports advanced data types such as JSONB, full ACID transactions, and rich indexing, which makes it well suited as the system of record for DBCAS.
[P074] [Normal] PostgreSQL provides high performance and scalability through features such as MVCC, cost-based query optimization, and parallel query execution. For DBCAS, it stores the concept taxonomy, the question bank, practice session state, attempts, and per-concept competency results.
[P075] [Normal] In PostgreSQL, data is organized into tables with well-defined schemas. Constraints such as primary keys, foreign keys, unique constraints, and default values enforce data integrity across the 41 tables of the DBCAS schema, while JSONB columns keep flexible evidence payloads — grading detail, selection decisions, immutable snapshots, and cached LLM responses — queryable.

[TABLE 03] style=Table Grid rows=42 cols=2
  [R00] Table Name | Short Description
  [R01] Account | Stores login credentials for learners and administrators, including email, password hash, account status, password-set/change flags, the role-management capability flag, and creation date.
  [R02] Role | Defines the two system roles used for role-based access control: Learner and Administrator. The User role is implemented as Learner and the Admin role as Administrator.
  [R03] AccountRole | Junction table resolving the many-to-many relationship between Account and Role, recording role assignment timestamps.
  [R04] UserProfile | Holds personal details of users linked one-to-one to their Account (full name, student code, phone, date of birth); identifying fields are stripped before any external LLM call (NFR-07).
  [R05] CourseLearningOutcome | Course learning outcomes (CLOs) defined by administrators and aligned to the university database course curriculum (FR-02).
  [R06] Concept | The Core PostgreSQL concept model, organized by subject area with a base difficulty level and sql_feature, keywords and learning objectives used for practice selection and recommendations (FR-02, FR-14).
  [R07] CLOConcept | Junction table mapping course learning outcomes to PostgreSQL concepts; records whether each mapping was set by an administrator or suggested by assistive AI, and its confirmation status (FR-03).
  [R08] Question | The Administrator-approved, validated question bank: multiple-choice, SQL, and short essay items with prompt, reference answer, explanation, difficulty, points, provenance tags and source references, source (bank or AI-generated), lifecycle status, and family/version lineage (FR-04).
  [R09] QuestionConcept | Junction table tagging questions with PostgreSQL concepts, including whether a technique is mandatory and the review status of AI-recommended tags, which remain unconfirmed until reviewed by an administrator (FR-05, FR-09).
  [R10] MCQOption | Answer options for multiple-choice questions, including the verified correct-answer flag used for instant grading (FR-08).
  [R11] SQLTestDataset | Test datasets for practical SQL questions: setup SQL executed inside the Docker sandbox and expected result sets, including edge cases (FR-09).
  [R12] Rubric | Grading rubric levels (Complete, Mostly Complete, Partial, Incomplete) with score ranges and criteria for rubric-guided essay evaluation (FR-10).
  [R13] Assessment | Legacy prebuilt assessment definition retained for historical rows only: question count and duration, target type mix, historical release policy and family/version lineage. Migration 019 closes published definitions; no current API creates one.
  [R14] AssessmentConcept | Legacy junction table holding the target concepts of a retired assessment, their allowed difficulty range, and its passing benchmark; current learner-defined practice snapshots a 70% target in the session configuration.
  [R15] AssessmentSession | One learner's practice run: status, frozen configuration snapshot (including bank/AI source), optional legacy assessment id (nullable since migration 018), question locale, start and expiry times, submission time, start-request id, and review/release status, including automatic submission when the timer reaches 00:00 (FR-07).
  [R16] Attempt | One row per served question: the learner's answer (selected option, SQL text, or essay text), an immutable question snapshot, draft state, grading status, the graded score, and standardized grading evidence (FR-11).
  [R17] SelectionLog | Audit log of every question-selection decision (chosen concept, difficulty, question type and whether a fallback item was used), used to monitor selection quality (FR-15, RSK-06).
  [R18] ConceptCompetency | Per-concept competency result of a session: points earned vs. points possible on a widened two-decimal scale, the computed percentage, and the below-target flag (FR-12, FR-13).
  [R19] CompetencyGap | Concepts flagged as gaps and their LLM-generated explanations, with a context hash so identical sanitized explanations are reused. The ranked study list is derived from ConceptCompetency and the session's frozen concept targets (70% for learner-defined practice), ordered by target_pct minus competency_pct; it is not stored separately (FR-14).
  [R20] LLMCache | Cached external LLM responses keyed by a hash of the sanitized request, used to reduce API cost and latency (RSK-03).
  [R21] QuestionCandidate | AI-generated drafts held outside the Question bank; automated checks cover answer completeness, duplicates, and SQL task/reference-answer execution on test datasets. An Administrator then approves the candidate before it is stored as a validated Question and becomes servable (FR-15, NFR-09).
  [R22] AccountIdentity | Google/GitHub identity for sign-in and sign-up, with provider user id and verified-email flag. Matching verified emails link one account; new accounts receive Learner.
  [R23] AccountRoleAudit | Immutable audit trail of role grants, revocations and the one-time role-manager bootstrap, including actor, target, and previous/new role.
  [R24] OAuthHandoff | Single-use, short-lived hashed handoffs exchange a verified Google/GitHub identity for rotating access/refresh sessions without tokens in URLs.
  [R25] LoginThrottle | Server-side brute-force protection: hashed login keys with recent failure timestamps and an expiry window.
  [R26] ConceptDependency | Directed prerequisite edges between concepts (prerequisite to dependent concept); duplicate edges are blocked by the primary key and cycles are checked by the service layer.
  [R27] QuestionTranslation | Locale-specific (for example Vietnamese) prompt, explanation, option texts and rubric criteria for a question; English remains canonical on Question, MCQOption and Rubric.
  [R28] SessionQuestionPlan | Frozen ordered list of questions reserved for a practice session, including items not yet served, so later bank edits cannot alter an in-progress session; the complete plan is stored before question one (FR-15).
  [R29] SessionStartRequest | Idempotency ledger binding each learner's start or resume request id to a session, replayable after the session has completed.
  [R30] GradingJob | Durable work queue and lease for SQL and essay grading, with retry counters, availability time and failure classification.
  [R31] GradeReview | Human review decision for the mandatory administrator approval: automated evidence, reviewer, approved score and comments.
  [R32] ResultReleaseEvent | Immutable history of every session release-status transition (auto grading, pending review, reviewed, published, grading failed).
  [R33] AssessmentBlueprint | Legacy, versioned evidence mix of a retired formal definition: subject area, band, question counts, scoring weights, evidence types and approval basis. Kept for historical sessions only.
  [R34] AdaptiveEvent | Historical audit of adaptive batch or decision events, including mid-session shortage notices; retained for sessions created before learner-defined practice.
  [R35] PasswordResetToken | Single-use, short-lived password-reset tokens stored only as SHA-256 digests, with expiry, use and revocation timestamps.
  [R36] PasswordResetAudit | Immutable audit trail of password-reset requests and completions.
  [R37] AssessmentQuestion | Legacy junction table listing the curated exam question pool of a retired assessment (migration 017); unused by learner-defined practice.
  [R38] EvaluationRecord | Standardized grading evidence for one answer or scope: question snapshot, rubric result, points, evaluator source, hashes and validation flags.
  [R39] GradeEditAudit | Immutable audit of every manual grade change: attempt, reviewer, old and new score, reason and timestamp.
  [R40] RefreshSession | Hashed refresh-token families for email and OAuth sign-in, with credential version, expiry, use and revocation timestamps.
  [R41] SystemSetting | Runtime settings row retained for historical/operational values; result release is no longer selectable.
