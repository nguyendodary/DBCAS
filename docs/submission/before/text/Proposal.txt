[P059] [Heading 1] 1. Project Title
[P060] [Normal] Project Title: DBCAS – AI-Assisted Database Competency Assessment and Skill Gap Analysis
[P061] [Normal] Field of Study: Educational Technology, Database Systems, Software Engineering, Applied Artificial Intelligence.
[P062] [Normal] Academic Affiliation: Capstone Project 1, Team C1SE.70, International School, Duy Tan University.
[P063] [Normal] Project Timeline: September 14, 2026 – December 26, 2026 (Fall Semester 2026).
[P064] [Normal] Target Audience: Undergraduate students taking relational database courses and computing disciplines requiring structured database design and querying skills.
[P065] [Normal] DBCAS is an educational web application designed to help university learners and academic administrators get a clear, detailed picture of database skills. In regular university courses, exams and quizzes usually give students just one overall score, such as 7 or 8 out of 10. While this number shows whether a student passed, it does not explain which specific topics they understand well and where they need more practice. For example, two students might receive the exact same grade, but one is good at writing SQL queries while struggling with database normalization, and the other has the opposite problem. A single overall grade treats both students as if they have identical skills, which makes it hard for them to know what to study next.
[P066] [Normal] To solve this problem, DBCAS connects course learning goals to the Core PostgreSQL Knowledge Domain: SQL querying, data manipulation and definition, integrity constraints, views, and database design fundamentals. Before a session, learners choose the skills to be assessed and one or more difficulty bands (EASY 1–2, MEDIUM 3, or HARD 4–5). Each practice session lets the learner choose the concepts, difficulty bands, question count (1–20, default 5) and source (validated bank or AI), and the session expires after 30 minutes. Each session fixes its skills, difficulty bands, question source and length before question one. The system assembles and freezes the complete question plan at that moment, so the plan is spread across the selected concepts as far as the count allows, the exact count is met with the formats available, and question versions are not duplicated. With source AI, the planner requests MCQ and essay items from the model and always takes SQL items from the validated bank; if AI cannot fill the plan, a single bank_mixed notice explains the substitution. The three question formats are multiple-choice questions, read-only SQL queries run in a secure PostgreSQL 17 Docker sandbox, and short conceptual written answers evaluated using clear grading rubrics. The system combines answer evidence into a per-concept competency profile. After the radar and bar charts, it shows a “What to study next” list of below-benchmark concepts ranked by the size of each shortfall; each item names the concept and shows its description when available. Every submitted session is graded and evaluated by AI, then reviewed and approved by an administrator before the official result is published, and the learner's cumulative profile pools evidence from published sessions only.

[P076] [Heading 1] 4. Problem Statement
[P077] [Normal] In Computer Science and Software Engineering degree programs, the Database Systems course is a required core subject. Students must learn both practical SQL coding and conceptual database design. However, traditional grading in university courses faces several key problems:
[P078] [Heading 2] 4.1. One Overall Grade Hides Real Strengths and Weaknesses
[P079] [Normal] Typical exams give a single total score. For instance, two learners might both score 7.5 out of 10. Learner A writes SQL joins easily but struggles with normalization rules. Learner B designs good Entity-Relationship diagrams but makes syntax mistakes with SQL GROUP BY queries. Even though their skills and study needs are completely different, standard grading gives them the exact same score. Neither learner knows what they need to work on.
[P080] [Heading 2] 4.2. Lack of Detailed Explanations for Mistakes
[P081] [Normal] When learners receive graded tests or online quizzes, they usually only see whether an answer was right or wrong. They do not get a clear explanation of why an answer was wrong, which core concept they misunderstood, or what topics they should review before moving into advanced classes like Web Development or Enterprise Systems.
[P082] [Heading 2] 4.3. Heavy Grading Workload in Large Classes
[P083] [Normal] In university classes with 50 to 70 learners per class, course instructors and teaching assistants have very little time. Checking SQL queries by hand takes hours, and grading written conceptual explanations for dozens of learners is time-consuming and can lead to inconsistent scores when graders get tired.
[P084] [Heading 2] 4.4. Problem Identification Through Online Research
[P085] [Normal] Our team did not conduct direct student interviews or surveys. Instead, we explored the problem by researching developer discussion forums, programming education communities, and technical learning articles online (such as discussions on Stack Overflow, Reddit threads on r/learnprogramming, and computer science teaching blogs). By looking into what learners and educators discuss online, we identified several recurring difficulties that learners experience when learning databases. These common online discussions helped shape our project idea and confirmed the need for DBCAS:
[P086] [Caption] Table 3: Common Database Learning Difficulties Identified from Online Research
[P088] [Heading 2] 4.5. How DBCAS Solves These Problems
[P089] [Normal] To address these real-world challenges, DBCAS uses three practical assessment methods: instant scoring for multiple-choice questions, an isolated Docker container sandbox to run read-only learner SQL safely, and rubric-guided AI evaluation for short conceptual answers. Before the session starts, the learner fixes the concepts, difficulty bands, question count and source. The system then draws only content-validated items — from the approved bank, or from validated AI generation for MCQ and essay items — so every question is relevant, the plan is spread across the selected concepts as far as the count allows and no question family repeats; the complete plan is frozen at that point and SQL items always come from the validated bank. Answers are graded on submission and the resulting evidence builds a competency profile without relying on hidden or unexplained grading rules. Every submission is reviewed by an administrator—SQL and essay scores are checked or adjusted and the result is approved—before it is published.
[P090] [Heading 1] 5. Survey / Existing Solutions
[P091] [Normal] We reviewed existing educational tools and grouped them into three main types to see how they handle database learning and assessment:
[P092] [Heading 2] 5.1. Online Query Practice Sites
[P093] [Normal] Websites like LeetCode, HackerRank, SQLZoo, and DataCamp allow learners to write SQL queries and compare their output against expected results. They are great for quick syntax practice. However, their scope is limited: they only check SQL queries, offering no support for Entity-Relationship modeling or database normalization theory. Also, their feedback only says 'Accepted' or 'Wrong Answer' without explaining the reasoning behind an error, and they do not link results to university course goals.
[P094] [Heading 2] 5.2. Traditional Learning Management Systems (LMS)
[P095] [Normal] Systems like Moodle, Canvas, and Blackboard organize course materials and gradebooks well. However, their test tools usually return just one total score. They cannot run and test learner SQL code safely, and instructors must grade written answers by hand. They also do not point out specific competency gaps or tell learners what to review next.
[P096] [Heading 2] 5.3. Conversational AI Chatbots
[P097] [Normal] General-purpose AI chatbots are useful for asking questions during study sessions. However, they are not designed for formal school exams. They do not have structured test workflows, can give different scores for similar answers, and cannot track learner skill progress over an entire semester.

[P100] [Normal] Key Advantages of DBCAS: DBCAS connects course learning outcomes directly to core PostgreSQL concepts. By testing learners through multiple question types, freezing a personalized practice plan before question one, showing visual competency profiles, and presenting a ranked list of weak concepts to study next, the platform gives both learners and administrators a more useful learning experience.

[P161] [Heading 2] 12.1. System Context Diagram
[P162] [Normal] Figure 2 shows DBCAS, its two human actors, and the external systems it depends on: the LLM Provider, the OAuth Identity Provider and email delivery. Directed flows cover registration and sign-in, practice setup and responses, curriculum management, analytics, password-reset mail, and assistive AI requests and results:
[P164] [Caption] Figure 2: DBCAS System Context Diagram
[P165] [Normal] The System Context Diagram defines the high-level operational boundary of DBCAS and captures its interactions with exactly two human actors and three external software systems: the LLM Provider, the OAuth Identity Provider and the email delivery service.
[P166] [Normal] •  Learner (Primary Human Actor): An undergraduate student taking database assessments. Learners sign in with email/password or Google/GitHub OAuth, recover a forgotten password through a single-use emailed link when mail delivery is configured, choose their concepts, difficulty bands, question count and source for practice sessions, and submit multiple-choice responses, read-only SQL queries, and written conceptual answers to DBCAS. In return, they receive visual competency profiles across core PostgreSQL concepts (including cumulative published results), evidence-linked competency-gap explanations, a prioritized list of topics to study, and results released after administrator review and approval.
[P167] [Normal] •  Administrator (System Content Manager): An authorized DBCAS Administrator responsible for academic content and system configuration. Administrators define Course Learning Outcomes (CLOs), configure the PostgreSQL concept model and prerequisites, set difficulty levels, approve AI-generated questions after automated checks, curate the validated question bank and scoring rubrics, configure system settings, manage roles (Administrator-only accounts cannot take practice sessions), and review SQL and essay grades for every submission before publication; an Administrator can never review or publish a result for a session they own. In return, they receive cohort-wide competency gap analytics, individual learner performance records, and system-proposed CLO-to-concept mappings for review.
[P168] [Normal] •  LLM Provider (External Software System): An external software service (a provider-agnostic REST API; any compliant LLM vendor may be used) connected via secure API calls. The LLM Provider is utilized strictly for assistive AI analysis: recommending connections between CLOs/questions and PostgreSQL concepts, evaluating short technical essays against administrator rubrics, and generating plain-language explanations of detected skill gaps.
[P169] [Normal] Role mapping and separation: DBCAS defines exactly two application roles. The User role is implemented as Learner, and the Admin role is implemented as Administrator. There is no third role. Self-registration and OAuth create Learner accounts only; Administrator accounts are provisioned by an existing role manager and start disabled. Administrator accounts cannot start, serve or submit a practice session, and an Administrator cannot review or publish a result for a session they own. A Learner may request promotion to Administrator through the course team; an existing Administrator with role-management capability reviews the request and grants or denies it through the audited role-management function. DBCAS does not expose a self-service promotion endpoint, and promotion never happens automatically.
[P170] [Normal] •  OAuth Identity Provider (External Software System): Google and GitHub OAuth 2.0 authorization servers used for sign-in and learner sign-up. DBCAS validates a signed state value, applies PKCE for Google, exchanges the authorization code server-side, requires a verified email, and never stores provider access tokens. New OAuth identities become Learners and never receive an Administrator role automatically.
[P171] [Normal] •  Email Delivery Service (External Software System): SMTP delivery used only for single-use password-reset links; when SMTP is not configured the reset endpoints report that mail is unavailable.
[P172] [Normal] •  DBCAS (System Under Study): The central educational software platform that coordinates learner-defined practice sessions, freezes the selection and complete question plan before serving, executes read-only SQL queries in a sandboxed environment, stores standardized evaluation evidence, computes competency scores deterministically, supports a mandatory AI-then-administrator review workflow, pools published evidence into a cumulative profile, and visualizes competency profiles.
[P173] [Normal] Architectural Boundary & Technology Encapsulation: In strict alignment with system context modeling standards, Figure 2 maintains a high-level view and does not include internal software modules, database engines, application frameworks, or development toolchains as external actors. The OAuth Identity Provider and the Email Delivery Service are drawn in Figure 2. Implementation technologies (such as React, Vite, Tailwind CSS, Chart.js, FastAPI, PostgreSQL, Docker, and Git) and internal processing modules (Personalized Plan Assembly, Scoring Engine, Evidence Store, Competency Engine, Competency Gap Analyzer, and Review/Publish workflow) operate wholly within the logical architecture of DBCAS and are detailed in Section 12.2.
[P174] [Normal] AI Ethics & Administrator-Configured Evaluation Principle: In strict compliance with academic ethics, fairness, and transparency, the external LLM Provider functions solely as an assistive component and never autonomously determines a learner's final competency. Administrators configure essay rubrics and review every submission; the platform applies a 70% passing target per concept. LLM-assisted essay scores are recorded as answer evidence, and DBCAS applies predefined rules to aggregate that evidence into final concept competency scores and rank below-benchmark concepts by shortfall. Every submission is reviewed and approved by an administrator before publication, and every review and release transition is auditable. LLM-generated gap explanations link to answer evidence and do not change scores or recommendation order. AI-generated question delivery is an optional source mode: it requires a configured provider, generates MCQ and essay items while SQL stays bank-only, and fails closed with an explicit unavailable response rather than serving an unvalidated item.
[P175] [Heading 2] 12.2. Multi-Tier Logical System Architecture
[P176] [Normal] DBCAS is organized into four main layers to keep components clean, easy to test, and simple to maintain, as illustrated in Figure 3:
[P178] [Caption] Figure 3: DBCAS Logical System Architecture Diagram
[P179] [Normal] Note: Figure 3 shows the baseline four-tier layout. OAuth sign-in, personalized plan assembly, durable asynchronous grading, and the administrator review/publish workflow operate within the Application & Services and Data & Storage tiers.
[P180] [Normal] The four architectural tiers operate as follows:
[P181] [Normal] •  Presentation Tier (Web Frontend): A single-page web app built with React.js and Vite using JavaScript (ES6+ / JSX), styled with Tailwind CSS, and using Chart.js for data visualization. Includes learner portals for practice sessions, results, and radar charts; administrator portals for managing CLOs, questions, rubrics, and result review and approval; the code editor for SQL queries; and English/Vietnamese and theme preferences.
[P182] [Normal] •  Application & Services Tier (FastAPI): A Python backend handling application logic through dedicated services: JWT authentication, OAuth sign-in and role management with immutable audit, personalized plan assembly, session coordination with autosaved drafts, validated question bank management, grading engines with durable retry jobs, mandatory administrator review and result publication, competency scoring and cumulative aggregation, gap detection, and study-topic ranking.
[P183] [Normal] •  Data & Storage Tier: A PostgreSQL 17 database (41 tables) storing users and roles, course outcomes, questions and translations, test attempts, immutable evidence, review and release audit records, competency results, and cached LLM responses. Short-lived JWT access tokens and a PostgreSQL refresh-session table provide rotation and revocation without a separate session service.
[P184] [Normal] •  External AI & Execution Sandbox: A dedicated Docker container hosting an isolated PostgreSQL instance for read-only learner SQL, with strict memory and runtime limits; every query executes inside a read-only transaction that is rolled back after evaluation. External language model APIs (provider-agnostic) evaluate written conceptual answers using structured administrator rubrics, and OAuth 2.0 authorization servers support sign-in and learner sign-up without storing provider tokens or exposing them to the browser.
[P185] [Heading 2] 12.3. Evidence-Based Competency & Gap Evaluation Pipeline
[P186] [Normal] The central data flow in DBCAS turns learner answers into deterministic competency evidence through a personalized assessment pipeline, as shown in Figure 4:
[P188] [Caption] Figure 4: Evidence-based Competency & Gap Evaluation Pipeline
[P189] [Normal] Note: Figure 4 shows the baseline evaluation pipeline. In the implemented system the complete practice plan is assembled and frozen before the first question is served, learner SQL is read-only and always drawn from the validated bank, and results are published only after the mandatory administrator review and approval.
[P190] [Normal] How the Evaluation Pipeline Operates: Before a session, the learner selects the skills to be assessed and one or more difficulty bands. The system fixes the skills, bands, question source and length before question one and draws only content-validated items (approved bank or auto-validated AI-source items) with confirmed concept tags, spreading the plan across the selected skills as far as the count allows and never repeating a version family. A practice session freezes its complete plan at that point, meeting the exact length with the formats the bank allows. The complete plan is assembled from the validated bank (and, in AI mode, from generated MCQ and essay items) and frozen before question one. When the bank cannot supply the requested count, the start stops with an explicit shortage explanation instead of reducing the count or relaxing validation. Answers are scored on submission by format. MCQs use verified keys; read-only SELECT statements run in the Docker sandbox against expected rows and columns; essays use LLM assistance and the four-level administrator rubric. Scores become concept-linked evidence, with drafts autosaved and navigation moving forward only. Bank candidates are prepared before sessions; in AI source mode, the generator produces and validates MCQ and essay items at session start. The system checks answer completeness and duplicates, and for SQL items it runs the task and reference answer against test datasets. An Administrator reviews the question, answer, concept tags and difficulty; only approved items enter the validated bank, which is the default source for sessions. In AI mode the generator supplies MCQ and essay items only; SQL items always come from the validated bank. Every generated question is validated before it enters the frozen plan, and a single bank_mixed notice is shown when bank items fill part of the plan. When the session ends at the configured length or at the configured deadline, final competency is computed deterministically. Concepts below the platform's 70% passing target are ranked by shortfall and shown as the “What to study next” list. Every result is published only after an administrator reviews the SQL and essay scores, adjusts them if needed, and approves it. The learner's cumulative profile pools evidence from published sessions only. The LLM may add evidence-linked explanations but does not affect scores or topic order.
[P191] [Heading 2] 12.4. Multi-Format Practice & How Scores Are Calculated
[P192] [Normal] To ensure fair, understandable grading, DBCAS avoids mysterious black-box calculations. Instead, each question has an assigned point value and is linked to the specific PostgreSQL concepts it tests. When a practice session is submitted:
[P193] [Normal] •  Multiple-Choice Questions: Scored automatically based on the verified correct answer chosen by the administrator.
[P194] [Normal] •  Practical SQL Queries: Read-only SELECT statements are executed inside the isolated PostgreSQL 17 Docker sandbox and graded semantically, never by exact string matching. Points are awarded deterministically for syntax validity, correct results across multiple test datasets including edge cases, and required-concept compliance when the question mandates a technique — equivalent SQL formulations receive full credit. DML/DDL are never executed; that knowledge is assessed through MCQ and essay items.
[P195] [Normal] •  Short Conceptual Essays: Evaluated against a clear rubric with LLM assistance, checking whether the learner correctly explained key concepts, noted trade-offs, and cited proper technical terminology.
[P196] [Normal] Deterministic Scoring & Human-Governed Competency: To calculate a learner's standing on any given PostgreSQL concept (such as JOINs or Window Functions), the system computes scores deterministically by comparing points earned on items testing that concept against total possible points available for it. The cumulative profile pools point totals across every published session instead of averaging session percentages. If a learner's competency on a concept is lower than the platform's 70% passing target, the system flags it as a competency gap. After showing the profile, DBCAS ranks those concepts by their shortfall from the target and presents them as study topics, using the concept name and its description when available to clarify what to review. The LLM Provider only generates evidence-linked, plain-language explanations; it does not determine the score or the topic order. An administrator reviews the SQL and essay scores and approves every result before it is published; every review and release transition is recorded in an immutable audit trail.

DBCAS applies fixed rules to recorded answer evidence to compute concept competency and rank gaps by shortfall; gap explanations do not change scores or order.
