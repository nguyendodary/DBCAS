--- db-easy-weak-entity [mcq d2]
P: In an ER model, a dependent entity can exist only while its owning entity exists, and its identifying key includes the owner's primary key. Which relational mapping is correct?
A. Give the dependent table its own surrogate primary key and omit the owner key, because a surrogate key makes the owner unnecessary.
B. Add a nullable foreign key to the owner and allow dependent rows that reference no owner, because NULL means 'not yet assigned'.
C. Store the dependent rows as a comma-separated list in a column of the owner table, because the dependency is one-to-many.
D* Use a composite primary key made of the owner's primary key plus the dependent entity's partial key, with a foreign key to the owner.
E: A weak entity is identified through its owner: the owner key is part of the weak entity's primary key and also a foreign key. The composite key prevents two owners from sharing partial-key values, and the foreign key plus deletion rules preserve existence dependence. A surrogate key alone does not encode the identifying relationship; a delimited list is non-atomic; and a nullable foreign key contradicts the stated existence dependency.

--- db-hard-bcnf-dependency-loss [mcq d4]
P: Relation R(A,B,C,D) has functional dependencies AB -> CD and D -> A. A BCNF decomposition produces R1(A,D) and R2(B,C,D). Which statement is correct?
A* The decomposition is lossless but does not preserve AB -> CD.
B. The decomposition is lossless and preserves AB -> CD.
C. The decomposition is lossy because A and B are placed in different relations.
D. No BCNF decomposition of this relation exists, so the question is ill-posed.
E: The candidate keys are AB and BD: AB+ is all attributes, and BD+ reaches A through D -> A and then C through AB -> C. D -> A violates BCNF. The split has common attribute D, and D -> A makes D a key of R1, so the join is lossless. R2 has no nontrivial projected dependency, but AB -> CD cannot be checked inside either relation because it needs A from R1 and B,C,D from R2. BCNF decompositions therefore need not preserve dependencies.

C. {AB}
D. {AB, AC, AD, AE, BC}

AE+ reaches B through E -> B, C through AB -> C, and D through C -> D, so AE is a key. No pair without A determines all attributes: BC+ lacks A and every other pair is smaller. E: The given FDs form a minimal cover, so synthesis creates one relation per dependency: (A,B,C), (C,D), (D,E). The candidate key AB is contained in R1, so no extra key relation is needed. --- db-hard-category-tree [sql d4]
P: Table category(category_id INT PRIMARY KEY, name TEXT NOT NULL, parent_id INT) represents a self-referencing one-to-many relationship; NULL parent_id marks a root. Rows whose parent chain never reaches a root are not returned. Order by depth ascending, then category_id ascending.
REF: WITH RECURSIVE tree AS (SELECT category_id, name, 0 AS depth, name AS root_name FROM category WHERE parent_id IS NULL UNION ALL SELECT c.category_id, c.name, t.depth + 1, t.root_name FROM category c JOIN tree t ON c.parent_id = t.category_id) SELECT category_id, name, depth, root_name FROM tree ORDER BY depth, category_id
E: The recursive term starts from roots and adds one level per iteration while carrying the root name, which implements the parent-child relationship without assuming a fixed depth. In the edge dataset the two roots are returned with the same name, which is legal because names are not keys, and the orphan whose parent does not exist is unreachable and therefore excluded. ORDER BY makes the result deterministic across executions.
