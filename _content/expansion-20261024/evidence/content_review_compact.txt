--- Q645 [a2-easy-index-tradeoff] MCQ d2 | IDX
P: A B-tree index is added on a frequently filtered column. Which statement best describes the effect?
A* Lookups of matching rows can become faster, but the index uses storage and adds work to inserts, updates and deletes, and the planner may still choose a sequential scan.
B. Every query on the table becomes faster because the planner must use the newest index.
C. Write operations become faster because the index organizes new rows before they are stored.
D. The index also guarantees that the column is unique.
E: An index is a trade-off: it can make selective reads cheaper but consumes space and must be maintained on writes, so bulk changes can slow down. The planner compares costs and may ignore the index, for example when most rows match or the table is small. Only a UNIQUE index or constraint enforces uniqueness.

--- Q646 [a2-easy-composite-leftmost] MCQ d2 | IDX
P: A composite B-tree index is created on (customer_id, created_on). Which predicate can use it efficiently?
A* A filter on customer_id, or on customer_id together with a range on created_on, because the leading column is constrained.
B. A filter on created_on alone, because it is part of the index.
C. Any filter on any column of the table, because the index covers the whole row.
D. Only a filter that constrains both columns to equality; a range on created_on makes the index unusable.
E: A B-tree on (customer_id, created_on) is ordered by customer_id first, then created_on within each customer. It can be used when customer_id is constrained, optionally with a range on created_on. A predicate on created_on alone cannot use the index efficiently because the leading column is unconstrained. Equality on both columns works, but a range on the trailing column is also supported.

--- Q647 [a2-easy-index-write-cost] MCQ d1 | IDX
P: Why does adding several indexes to a table slow down INSERT, UPDATE and DELETE statements?
A* Every affected index must be updated to reflect the changed rows, so more indexes mean more maintenance work per write.
B. Indexes lock the entire table on every write, so only one writer can proceed at a time.
C. PostgreSQL rewrites every index from scratch after each write.
D. Indexes copy the full table, so each write is duplicated once per index.
E: Each index is a separate data structure keyed on its columns. An insert or a change to an indexed column requires an entry in every affected index, which adds I/O and CPU work. Writers are not serialized by a table-wide lock, indexes are updated incrementally rather than rebuilt, and an index stores keys and row references, not a copy of the table.

--- Q648 [a2-medium-expression-index] MCQ d3 | IDX
P: Queries run WHERE lower(email) = 'a@example.com' on a large table that has a plain B-tree index on email. Why is the index not used, and what helps?
A* The expression lower(email) is not the indexed value, so an expression index on lower(email) is needed to match the predicate.
B. The index is not used because B-tree indexes never support text; only hash indexes do.
C. The index is ignored only when email is nullable; adding NOT NULL makes lower(email) use the plain index.
D. Nothing helps: PostgreSQL cannot index the result of any function.
E: A plain index on email stores email values, while the predicate compares lower(email). The planner would need an index whose key is the same expression, created as CREATE INDEX ... ON t (lower(email)). PostgreSQL supports expression indexes, and the function used must be immutable. Nullability and the B-tree text support are not the reason.

--- Q649 [a2-medium-partial-index] MCQ d3 | IDX
P: A status column is 'pending' for about 1% of rows, and almost all queries filter status = 'pending'. Which index is the best fit?
A* A partial index with WHERE status = 'pending', which stores only the matching rows and is maintained only when the predicate holds.
B. A full B-tree index on status, because partial indexes are not usable for equality filters.
C. An index on every other column, because status has low cardinality and cannot be indexed.
D. No index at all, because a filter matching 1% of rows always uses a sequential scan.
E: A partial index is defined with a WHERE predicate; it contains only the rows satisfying that predicate, so it is much smaller than a full index and is only maintained for matching rows. Queries must include a predicate that implies the index predicate to use it. Low cardinality alone does not prevent indexing, and a highly selective filter is exactly where an index can help.

--- Q650 [a2b-easy-fk-no-index] MCQ d2 | IDX
P: A child table has a foreign key column customer_id referencing customers(customer_id). Does the foreign key automatically provide an index for queries that filter or join on the child's customer_id?
A* No. PostgreSQL does not create an index on the referencing column; add one when child lookups or parent deletes need it.
B. Yes. The foreign key creates a unique index on the child column.
C. Yes. The foreign key creates a B-tree index, but only for DELETE statements.
D. No, and an index on the child column is never useful because the constraint already optimizes joins.
E: A foreign key constraint enforces referential integrity; it does not create an index on the referencing side. When a parent row is deleted or its key changes, PostgreSQL must find child rows that reference it, and joins on the child column also need an index. Without one, those operations can scan the whole child table. Primary key and UNIQUE constraints are the constraints that create indexes automatically.

--- Q651 [a2b-easy-constraint-index] MCQ d2 | IDX
P: Which constraint automatically creates an index on the constrained column in PostgreSQL?
A* A PRIMARY KEY or UNIQUE constraint.
B. A CHECK constraint.
C. A FOREIGN KEY constraint.
D. A NOT NULL constraint.
E: PRIMARY KEY and UNIQUE constraints are enforced with a unique B-tree index, which is why lookups by the constrained columns are fast. CHECK and NOT NULL are validated per row without an index. A FOREIGN KEY is also validated without creating an index on the referencing column.

--- Q652 [a2b-easy-order-by-index] MCQ d2 | IDX

B. The index guarantees that only 20 rows are read from disk, regardless of any filters.
C. The index stores the full rows, so the table is never read.
D. The index makes the ORDER BY clause unnecessary in the SQL text.

--- Q653 [a2b-easy-selectivity] ESSAY d2 | IDX
P: A table has 2 million rows. Query A filters an indexed column matching about 0.1% of rows; Query B filters a different indexed column matching about 45% of rows. Explain why the planner may use an index for A but a sequential scan for B. Include selectivity, random I/O and the small-table case.
REF: A filter matching 0.1% of 2 million rows selects about 2000 rows. An index can locate those rows with relatively few page reads, so the random I/O is justified. A filter matching 45% selects about 900000 rows; visiting that many heap pages in index order causes many random reads and repeated page visits, while a sequential scan reads each page once in physical order. The planner compares estimated costs using statistics, so it may choose the sequential scan. For a small table, even a selective filter may use a sequential scan because the whole table fits in a few pages and the index lookup overhead is not repaid.

--- Q654 [a2b-easy-index-budget] ESSAY d2 | IDX

--- Q656 [a2b-medium-column-order] MCQ d3 | IDX

--- Q636 [adm-easy-wal-purpose] MCQ d2 | PG-WAL
P: Why does PostgreSQL write changes to the write-ahead log (WAL)?
A* WAL records are flushed before the corresponding data pages, so committed changes can be redone after a crash.
B. WAL stores a copy of every query plan so that frequently used queries skip planning.
C. WAL is only needed when streaming replication is enabled; a single server does not use it.
D. WAL keeps recent rows in memory so that SELECT statements avoid reading table pages.
E: WAL is the crash-recovery mechanism: change records are written and flushed before the modified data pages reach disk, so after a crash the server can replay committed changes. It exists independently of replication, although replication reuses the same stream. It is not a plan cache and not a row cache.

--- Q637 [adm-easy-streaming-standby] MCQ d2 | PG-REPLICATION

C. It receives the SQL text of SELECT statements and returns their results to the primary.
D. It receives committed row versions directly through shared memory and is always exactly current.
E: Streaming replication ships WAL records from the primary to the standby, which continuously applies them. A hot standby accepts read-only queries, and because applying can trail the primary, replica reads can be slightly stale. There is no shared-memory row transfer and no per-checkpoint logical dump.

--- Q665 [admb-easy-checkpoint-wal] ESSAY d2 | PG-WAL
P: Explain the relationship between WAL, COMMIT durability and checkpoints. Why does PostgreSQL not need to write every data page at commit, and how do checkpoints affect crash recovery time and I/O spikes?

--- Q666 [concb-easy-commit-guarantee] MCQ d2 | PG-TXN
P: What does a successful COMMIT guarantee?
A* The transaction's changes become visible and, with synchronous commit, its WAL is flushed before success is reported.
B. All dirty data pages of the transaction have already been written to their tables.

--- Q667 [concb-easy-dirty-read] MCQ d2 | PG-ISOLATION
P: What is a dirty read?
A* Reading data written by another transaction that has not committed; PostgreSQL's READ COMMITTED prevents it.
B. Reading the same row twice and getting the same values.
C. Reading a row that was committed after the reader's snapshot was taken.
D. Reading a table while another session holds a row lock.
E: A dirty read observes uncommitted data from another transaction, which could still roll back. PostgreSQL does not allow dirty reads at any supported isolation level; READ COMMITTED takes a new snapshot per statement and only sees committed data. Re-reading a row and getting the same values describes repeatable behaviour, while seeing newly committed rows is a non-repeatable or phantom phenomenon, not a dirty read.

--- Q668 [concb-easy-independent-rows] MCQ d2 | PG-LOCK

--- Q669 [concb-easy-disconnect] MCQ d2 | PG-TXN

--- Q670 [concb-easy-savepoints] ESSAY d2 | PG-TXN
P: Explain how SAVEPOINT works, including ROLLBACK TO SAVEPOINT and RELEASE, and give a realistic case where partial rollback is better than aborting the whole transaction.

After a later statement fails, ROLLBACK TO SAVEPOINT name undoes all changes made after the savepoint while keeping the transaction and the work before the savepoint alive. Savepoints create subtransactions, so using one per row has overhead and should be measured.

--- Q671 [concb-easy-optimistic-pessimistic] ESSAY d2 | PG-ISOLATION, PG-LOCK
P: Compare optimistic and pessimistic concurrency control in an application using PostgreSQL. Where does SELECT FOR UPDATE fit, and where do version checks plus retry or SERIALIZABLE transactions fit? Give one trade-off of each.
